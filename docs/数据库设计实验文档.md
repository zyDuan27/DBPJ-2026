# 校园活动报名系统：第四阶段报告

## 一、项目介绍

校园活动报名系统，覆盖用户登录、活动发布与审核、场地与分类字典、活动报名、候补递补、现场签到、活动评价、信用分流水和基础统计等功能。

目标数据库版本为 MySQL 8.4.8 LTS，字符集统一使用 `utf8mb4`。

## 二、关系模式

| 表名 | 说明 | 主键 | 关键约束 |
| :--- | :--- | :--- | :--- |
| `User` | 用户表，按 `role` 区分学生、组织者、管理员 | `user_id` | `phone` 唯一、`student_no` 唯一、角色检查 |
| `Campus` | 校区字典 | `campus_id` | `campus_name` 唯一 |
| `Venue` | 场地字典 | `venue_id` | 同一校区下 `venue_name + room_number` 唯一 |
| `Category` | 活动分类字典 | `category_id` | `category_name` 唯一 |
| `Activity` | 活动主表 | `activity_id` | 时间、容量、状态、场地冲突约束 |
| `Registration` | 报名记录 | `registration_id` | `student_id + activity_id` 唯一 |
| `ActivityFeedback` | 活动评价 | `feedback_id` | 一条报名记录最多一条评价 |
| `CreditRecord` | 信用分流水 | `record_id` | 同一报名记录同一原因只记一次流水 |
| `Notification` | 站内通知 | `notification_id` | 接收人外键、通知类型和已读状态检查 |

## 三、规范化与冗余检查

当前设计整体满足第三范式：

- `Campus`、`Venue`、`Category` 独立成字典表，活动表只保存外键，不冗余保存校区名、场馆名、分类名。
- `Registration` 只保存报名状态、候补序号、签到时间等报名事实，不保存学生姓名、电话和活动标题。
- `ActivityFeedback.activity_id`、`ActivityFeedback.student_id` 是可由 `registration_id` 推导的冗余字段，但它们直接支撑组织者反馈列表、学生个人评价查询和活动评分统计，属于明确的查询优化冗余，并由触发器校验其必须与报名记录一致。
- `CreditRecord.activity_id`、`CreditRecord.registration_id` 同样为信用流水追溯和统计保留。学生当前信用分不单独落在 `User` 表，而是通过 `100 + SUM(change_value)` 实时计算，避免维护两份信用分。
- `Activity.current_enrollment` 是性能型冗余字段，只统计 `ENROLLED` 与 `CHECKED_IN` 状态。该字段避免活动列表频繁聚合报名表，由后端报名事务统一维护，数据库检查约束兜底防止越界。

CREATE TABLE CreditRecord (
    record_id INT AUTO_INCREMENT PRIMARY KEY,

    CONSTRAINT fk_credit_operator FOREIGN KEY (operator_id) REFERENCES User(user_id) ON UPDATE CASCADE ON DELETE SET NULL,

    CONSTRAINT chk_credit_reason CHECK (reason_type IN ('CHECK_IN', 'ABSENT', 'MANUAL_ADJUST')),
    CONSTRAINT chk_credit_value CHECK (

        OR (reason_type = 'ABSENT' AND change_value < 0)

    )
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='信用分流水';

## 五、主要约束实现方案

外键级联策略：

- 校区删除时通过 `Venue.campus_id ON DELETE CASCADE` 删除下属场地；场地删除时通过 `Activity.venue_id ON DELETE CASCADE` 删除下属活动，活动再级联删除报名和评价，避免出现孤立业务数据。
- 分类删除时通过 `Activity.category_id ON DELETE CASCADE` 删除该分类下活动及其报名、评价等下游记录。
- 组织者和学生等用户主数据仍使用 `ON DELETE RESTRICT`，避免误删账号导致历史报名、反馈和信用主体不可追溯。
- `Activity.admin_id` 使用 `ON DELETE SET NULL`，管理员账号删除后保留活动审核记录主体。
- `Registration.activity_id` 使用 `ON DELETE CASCADE`，删除活动时同步删除报名记录。
- `ActivityFeedback.registration_id` 使用 `ON DELETE CASCADE`，报名记录删除时删除对应评价。
- `CreditRecord.activity_id`、`CreditRecord.registration_id`、`CreditRecord.operator_id` 使用 `ON DELETE SET NULL`，保留信用流水审计价值。
- 已初始化的旧数据库可执行 `sql/phase3_cascade_rules.sql`，将校区、场地、活动及活动下游记录的删除规则迁移到当前设计。

唯一性约束：

- `User.student_no`：学生学号唯一。
- `User.phone`：手机号唯一，可用于登录。
- `Campus.campus_name`：校区名称唯一。
- `Category.category_name`：分类名称唯一。
- `Venue(campus_id, venue_name, room_number)`：避免同一校区重复录入同一房间。
- `Registration(student_id, activity_id)`：同一学生对同一活动最多一条报名记录。
- `ActivityFeedback(registration_id)`：一条报名最多一条评价。
- `CreditRecord(reason_type, registration_id)`：同一报名记录的签到或缺勤信用流水只写一次。

检查约束：

- 用户角色限定为 `STUDENT`、`ORGANIZER`、`ADMIN`，且学生必须有学号，组织者和管理员不使用学号。
- 活动结束时间必须晚于开始时间，报名截止时间不晚于开始时间。
- 活动名额、场地容量必须为正数，当前报名人数不能超过名额。
- 候补记录必须有正数 `queue_no`，非候补记录必须清空 `queue_no`。
- 已签到记录必须有 `check_in_time`，非已签到记录必须清空 `check_in_time`。
- 评价评分限定为 1 到 5。
- 信用流水中签到为正分，缺勤为负分，人工调整允许正负。

触发器方案：

- `trg_activity_bi_validate`、`trg_activity_bu_validate`：校验组织者角色、审核人角色、活动名额不能超过场地容量，并阻止同一场地中待审核、已发布、进行中的活动时间重叠。
- `trg_registration_bi_validate`、`trg_registration_bu_validate`：校验报名用户必须是学生，且转入 `ENROLLED` 或 `CHECKED_IN` 时不能超过活动名额。
- `trg_feedback_bi_validate`、`trg_feedback_bu_validate`：保证评价只能来自已签到报名记录，且 `activity_id`、`student_id` 与报名记录一致。
- `trg_credit_bi_validate`：保证信用流水学生角色正确、操作人角色正确，并且签到/缺勤流水与报名状态一致。

## 七、多表查询优化

为了减少系统中的冗余数据，活动列表通过如下多表连接查询：

```sql
SELECT a.activity_id AS id, a.title,
       a.start_time AS startTime, a.end_time AS endTime,
       c.campus_name AS campusName, v.venue_name AS venueName, v.room_number AS roomNumber,
       cat.category_name AS categoryName,
       a.capacity_limit AS capacityLimit, a.current_enrollment AS currentEnrollment,
       u.username AS organizerName
FROM Activity a
JOIN Venue v ON a.venue_id = v.venue_id
JOIN Campus c ON v.campus_id = c.campus_id
JOIN Category cat ON a.category_id = cat.category_id
JOIN User u ON a.organizer_id = u.user_id
WHERE a.status IN ('PUBLISHED', 'ONGOING', 'FINISHED')
ORDER BY a.start_time DESC;
```

报名列表也不冗余活动标题和场地信息，而是从 `Registration` 连接 `Activity`、`Venue`、`Campus` 得到展示字段。这样可以避免场地、校区、分类名称变更时产生多表更新异常。

查询实现中的优化策略：

- 活动列表页的明细查询保留必要 `JOIN` 用于展示校区、场地、分类、组织者名称；对应的数量统计查询只保留 `Activity` 与筛选校区所需的 `Venue`，不再连接 `Campus`、`Category`、`User` 等仅用于展示的表。
- 学生“我的报名”和组织者“活动报名名单”的数量统计直接在 `Registration` 上按 `student_id`、`activity_id`、`status` 过滤，避免为了计数连接活动、场地或用户表。
- 场地列表查询使用 MyBatis 动态条件生成 `v.campus_id = ?` 和关键词条件，避免 `(参数 IS NULL OR 字段 = 参数)` 与空关键词 `LIKE '%%'` 干扰索引选择。
- 通知列表使用 `idx_notification_recipient_read_order` 覆盖 `recipient_id` 过滤和 `is_read ASC, created_at DESC, notification_id DESC` 排序，减少分页查询的额外排序成本。
- 所有自然语言查询最终都会编译成白名单 `SELECT`，并使用命名参数绑定、强制分页和角色权限条件注入，避免模型输出或用户输入直接拼接 SQL。
- 自然语言报名、签到、缺勤类查询显式从 `Registration` 使用 `idx_registration_activity_status_queue_time` 起步，避免优化器在小数据量下选择从 `User` 表扫描的低效计划。

项目提供 `sql/performance_checks.sql` 用于本地执行 `EXPLAIN`，覆盖活动大厅、组织者活动管理、报名名单、学生信用流水、通知列表和场地冲突检测等高频查询，便于验证查询计划是否命中上述组合索引。

## 八、自然语言查询设计

自然语言查询采用“LLM 理解 + 受控 QueryPlan DSL + 白名单 SQL 编译”的混合方案；模型不可用时降级到规则解析器。后端不执行模型直接生成的 SQL，只接受经过 `QueryPlanValidator` 校验的意图、字段、筛选条件、分页参数和排序计划。

实现要点：

- `LlmQueryPlanner` 调用 OpenAI-compatible Chat Completions API，要求模型输出固定 JSON 查询计划，不暴露真实表名和敏感字段。
- `QueryPlanValidator` 校验意图、字段别名、操作符、枚举值和分页上限；未知字段、非法操作符和写操作会被拒绝。
- `QuerySqlBuilder` 根据后端白名单模板生成 `SELECT`，所有用户输入和模型抽取值都通过命名参数绑定。
- 权限条件由后端根据当前角色强制注入，学生只能查询公开活动、自己的报名、自己的信用和通知；组织者只能查询自己活动相关数据；管理员可查全站业务数据。
- 对“查一下报名情况”“查询活动报名情况”等模糊表达，后端返回 `clarificationRequired=true` 和可点击追问选项。学生会得到“查询我的报名记录”等合法方向；组织者和管理员会基于数据库近期活动智能推荐“查询某活动的报名名单”等可能结果。

## 十、站内通知表补充

本轮新增 `Notification` 表承接站内通知能力，覆盖审核通过/驳回、活动取消、报名成功、进入候补、报名取消、候补转正、签到成功、缺勤记录等事件。通知只保存接收人、消息内容、已读状态和弱关联对象，不反向强依赖活动或报名记录，避免业务记录清理时破坏用户消息流。

```sql
CREATE TABLE Notification (
    notification_id INT AUTO_INCREMENT PRIMARY KEY,
    recipient_id INT NOT NULL COMMENT '接收用户',
    type VARCHAR(40) NOT NULL COMMENT '通知类型',
    title VARCHAR(120) NOT NULL COMMENT '通知标题',
    content VARCHAR(500) NOT NULL COMMENT '通知内容',
    related_type VARCHAR(40) COMMENT '关联对象类型：ACTIVITY / REGISTRATION',
    related_id INT COMMENT '关联对象 ID',
    is_read TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否已读',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    CONSTRAINT fk_notification_recipient FOREIGN KEY (recipient_id)
        REFERENCES User(user_id)
        ON UPDATE CASCADE
        ON DELETE CASCADE,
    CONSTRAINT chk_notification_type CHECK (type IN (
        'ACTIVITY_APPROVED', 'ACTIVITY_REJECTED', 'ACTIVITY_CANCELLED',
        'REGISTRATION_ENROLLED', 'REGISTRATION_WAITLISTED', 'REGISTRATION_CANCELLED',
        'WAITLIST_PROMOTED', 'CHECK_IN_SUCCESS', 'ABSENCE_MARKED'
    )),
    CONSTRAINT chk_notification_related CHECK (
        related_type IS NULL OR related_type IN ('ACTIVITY', 'REGISTRATION')
    ),
    CONSTRAINT chk_notification_read CHECK (is_read IN (0, 1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='站内通知';

CREATE INDEX idx_notification_recipient_read_order
    ON Notification(recipient_id, is_read, created_at DESC, notification_id DESC);
CREATE INDEX idx_notification_recipient_time
    ON Notification(recipient_id, created_at, notification_id);
```
